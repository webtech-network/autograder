# Terminal outcomes v1

`autograder.models.contracts.outcome` defines the shared HTTP, Python, and Action
artifact contract. Its JSON Schema is generated by `outcome_json_schema()`;
`validate_outcome()` enforces the additional arithmetic and semantic invariants.
Validation is required before external ingestion and persistence. One terminal
snapshot can be serialized and delivered repeatedly without evaluating again.

The version (`schema_version: "1.0"`) and discriminator (`status`) are required
on the wire. Timestamps require RFC3339 text with offsets; numeric Unix epochs
and date-only strings are rejected. The discriminator is `status`: `completed` requires a finite numeric `score` in
[0, 100], a typed `tree`, and a null `error`; `failed` requires null `score` and
`tree` and a structured error. Booleans and numeric strings are not scores.
Feedback and comparison independently carry `disabled`, `completed`, or `failed`
status. Completed enrichment has content and no error; failed enrichment has an
error and no content. Disabled enrichment has neither. A grading failure cannot
claim completed enrichment.

Every outcome identifies its execution and exact normalized definition through
`execution_id` and `provenance`. Error correlation IDs equal `execution_id`.
`started_at` and `finished_at` have explicit UTC offsets and serialize as UTC;
`duration_ms` is a nonnegative integer measured using a monotonic clock, frozen at
finalization, including engine resource cleanup. It excludes adapter queueing,
persistence, and publication. Internal
pipeline diagnostics are not public result fields.

Error codes are one closed vocabulary, `OUTCOME_ERROR_CODES` in
`autograder.models.contracts.outcome`; the terminal-outcome schema and OpenAPI
publish it as an enum, and every code below appears in it. Engine codes
(`ENGINE_ERROR_CODES`) are the only ones an evaluator or provider may raise as
`EvaluationError`; an unpublished code is a programming error reported as
`EXECUTION_ERROR`. Host-only codes (`HOST_ERROR_CODES`) are recorded by an adapter
for work the engine never finalized. `EXECUTION_ERROR` is the single code for an
unexpected failure in the engine and in every host.

| Trigger | Grading outcome | Error category / code |
| --- | --- | --- |
| An assessed criterion genuinely scores zero | Completed, score 0 | No top-level error |
| Student compilation/runtime failure or student execution timeout reported by an I/O evaluator | Completed, criterion scores 0 | No top-level error |
| Required preparation or assessment file missing | Failed, no score | submission / `REQUIRED_FILE_MISSING` |
| Preparation command fails because the submission does not satisfy it | Failed, no score | submission / `PREPARATION_FAILED` |
| Language omitted for a multilingual definition or disallowed language selected | Failed, no score | submission / `LANGUAGE_REQUIRED` or `LANGUAGE_NOT_ALLOWED` |
| Criterion file parameters conflict with its targets, or a target is outside the evaluation scope | Failed, no score | submission / `FILE_TARGET_CONFLICT` |
| A criterion target has a file type its evaluator does not accept | Failed, no score | submission / `UNSUPPORTED_FILE_TYPE` |
| A single-file evaluator matches several files without an explicit target | Failed, no score | submission / `AMBIGUOUS_FILE_TARGET` |
| AI criterion identities are not unique | Failed, no score | definition / `INVALID_DEFINITION` |

There is no partial grading policy: every configured evaluator is required,
including zero-weight criteria. A required evaluator failure makes the entire
numeric grade unauthoritative. Student timeout is determined by a sandbox's
explicit `TIMEOUT` assessment response; an exception while communicating with
the sandbox is an infrastructure failure. API evaluators assess returned HTTP
status/content; inability to obtain a response is a capability failure. These
conservative classifications avoid claiming that unavailable infrastructure
proved student code incorrect.

Public errors expose stable codes, fixed safe engine messages, categories
(`definition`, `submission`, `capability`, `provider`, `internal`), retryability,
and correlation IDs. Raw exceptions, provider responses, setup stderr, and
internal step names remain in host-controlled diagnostics/logs. Authenticated
external hosts may attest their own safe messages using the published codes; that
attestation does not prove the local server executed the grade.

The tree has one root representation. Categories retain the base/bonus/penalty
score semantics; holder scores must equal the weighted average of their children
and the root must equal the capped combination of its categories. Base weight is
100. Tests identify their evaluator and globally unique criterion `id`; display
names and grouping are presentation. Serialization rounds scores to two decimal
places, and validation allows only the resulting small arithmetic rounding
error. `outcome_score_vector(completed)` derives an ID-to-score projection from
the authoritative tree.

Scoring arithmetic has one definition (`autograder/models/contracts/scoring.py`):
effective sibling weights are ratios scaled to 100 (all-zero siblings share
equally; a mixed holder splits 100 by `subjects_weight`), holder scores are the
weighted mean of unrounded child scores, the final score is
`base + bonus/100*cap - (100-penalty)/100*cap` clamped to 0–100, every reported
score is rounded to two decimals and effective weights are not rounded. The
canonical criterion order is base, bonus, penalty and, inside a holder, nested
subjects before direct tests.

Every completed tree, locally produced or externally attested, passes the same
structural check, `verify_outcome_tree(criteria, tree)`: categories, holder names
and order, criterion IDs, evaluator types, labels and file targets must match the
definition, and effective weights must equal its ratios (tolerance 1e-5).
Reported `parameters` are optional on the wire; when present they must equal the
canonical parameters. Arithmetic is validated separately, from the reported
values, by the outcome model itself; neither check trusts the producer. No independently mutable vector is present on the wire.
The embedded `comparison` enrichment's `path` field carries a criterion ID, never
a display path. Tree parameters contain only normalized authoring parameters, never
pipeline-injected resources or prompts. Trusted detail may contain private tests;
student-facing visibility policy belongs to the hosting adapter.

Python terminal models are frozen, including nested JSON maps/lists. Their
`model_dump(mode="json")` output is an independent JSON-compatible delivery
payload. Modifying a payload does not modify the finalized grading snapshot.
The frozen `PipelineExecution` return envelope holds only `outcome`; intermediate
assessment data remains local to the coordinator. Optional diagnostic events
are separate from the grading artifact. Cleanup failures reach host logging and
an optional observer without replacing the completed or failed grading outcome.

Operationally, v1 outcomes replace legacy duplicate `root`/`tree` and HTTP
`children` wrappers. Stored legacy results are not automatically attested with
current definition hashes. Consumers migrate to the canonical outcome plus
compact polling/history projections; source files and trees require explicit
trusted detail retrieval.


## Size bounds

Student-controlled text cannot size an outcome. Each criterion `report` is at
most `MAX_REPORT_BYTES` (8 KiB) and feedback `content` at most
`MAX_FEEDBACK_BYTES` (256 KiB) of UTF-8, both in
`autograder/models/contracts/outcome.py`. The engine bounds locally produced
text in one place: `grade` excerpts every evaluator and AI report, and
`render_feedback` excerpts feedback. Text that fits is kept (lone surrogates
become U+FFFD). Longer text becomes a deterministic, valid UTF-8 excerpt that
keeps the head and the tail around a marker with the full byte count:

```text
FAILURE: Output Mismatch.
Expected: '5'
Actual: 'ooo...
[... 1040478 of 1048626 bytes omitted ...]
...ooo'
```

Excerpting never changes a score. Process output is still read with its 1 MiB
per-stream bound ([PROCESSES.md](PROCESSES.md)), and evaluators assess the whole
stream. Only the retained text is shorter. Validation rejects an attested report
or feedback above its bound with the typed error `text_too_large` and never
truncates it.

The worst-case outcome is a function of the definition, never of a submission.
`CompiledDefinition.max_outcome_bytes` is the largest size of any of its
outcomes serialized with `json.dumps` defaults. That encoding uses ASCII escaping
and spaced separators, so it is never smaller than a compact or raw-UTF-8
encoding:

```text
max_outcome_bytes = S + 6 * (N * 8 KiB + 256 KiB) + 1 KiB * nodes + 16 KiB
```

Here `S` is the measured tree with empty reports: IDs, labels, targets, weights
and canonical parameters. `N` is the number of criteria, and `nodes` counts
criteria, groups, categories and the root. The factor 6 is the largest JSON
escaping of one UTF-8 byte (`\u0001`). The per-node allowance covers score digits
and one attested comparison delta for each criterion of this definition. Deltas
for criteria `removed` since the baseline name criteria that are not nodes of
this definition and have no allowance. An attestation whose comparison lists
enough of them to exceed the bound is rejected with `OUTCOME_TOO_LARGE`. The
16 KiB covers identifiers, provenance, timestamps, statuses and a structured
error.

An attestation carries the definition snapshot and the outcome. Compilation
(`compile_definition` and `compile_snapshot`) therefore rejects with
`DEFINITION_TOO_LARGE` any definition whose snapshot plus `max_outcome_bytes`
exceeds `MAX_ATTESTATION_BYTES` (24 MiB, `verification.py`). The hosts' 32 MiB
request limit ([SUBMISSIONS.md](SUBMISSIONS.md)) leaves 8 MiB for identity and
audit metadata, so every valid definition's maximal attestation is accepted.
With short parameters this allows about 465 criteria, and long
definition-authored text lowers the number. The HTTP host also rejects an
attested outcome larger than its snapshot's `max_outcome_bytes` (for example
because of oversized `metadata`) with 422 `OUTCOME_TOO_LARGE`. Storage and UI can
size for these bounds.

Outcomes this host stored before the bounds existed are upgraded, never
rejected when they are read. Alembic revision `009_bound_outcome_text` rewrites
every stored `submission_results.outcome` with the same excerpt
(`bound_outcome_text`). Scores, identities and text within a bound are
unchanged, and the upgrade is idempotent. Publication receipts written before
the deployment are excerpted the same way when they are read, so their delivery
retry still completes and still equals the migrated row. Neither path applies to
incoming attestations.

## Publication receipts

The HTTP host writes each finalized outcome to a private, fsynced, atomically
renamed receipt before database publication. Set `WEB_OUTCOME_RECEIPT_DIR` to a
persistent writable directory (default `data/unpublished-outcomes`). Files have
mode 0600. A database failure retains the receipt and leaves the original grade
unchanged. Polling can remain processing until delivery succeeds.

Replay one receipt with the same database configuration:

```sh
python -m web.service.outcome_delivery /path/to/submission-receipt.json
```

Replay validates its bound submission provenance, publishes the existing outcome,
and removes the receipt only after success. Ambiguous commit recovery verifies an
identical persisted outcome; it never runs the pipeline. These receipts preserve
finished grading and do not provide a durable submission scheduler.


## Baseline comparison

Comparison is a separate, read-only use of two completed outcomes, never part
of grading. `compare_outcomes(baseline, head, baseline_definition, head_definition)`
is pure; the HTTP host exposes it as authenticated
`GET /api/v1/submissions/{submission_id}/comparison?baseline_submission_id={id}`
over two stored submissions of the same grading configuration. Nothing is
stored or regraded; a retry is another call. The grading outcome's `comparison`
enrichment stays `disabled` for normal grading and is never rewritten.

Each definition must hash to its outcome's provenance. Criteria join only by ID.
Same hash gives `same_definition` with an overall delta. Different hashes give
`cross_revision` with a null overall delta; per criterion, identical evaluator
type, normalized parameters, file target and effective weight/category compare
normally, changed effective weight/category is `reweighted` (with criterion
delta), changed type/parameters/target is `redefined` (no delta), and one-sided
criteria are `introduced`/`removed`. Failed or pending outcomes are
`OUTCOME_NOT_COMPLETED`; history without a bound snapshot or canonical outcome is
`LEGACY_UNVERIFIED`; different configuration resources are `NOT_COMPARABLE`.
Attested and executed outcomes follow identical rules and are labelled by
`source`. See [baseline comparison](../features/baseline_comparison.md) for the
complete table, example and migration notes.
